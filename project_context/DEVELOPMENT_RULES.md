# 1. Purpose

هذا الملف هو المرجع الرسمي لقواعد التطوير الخاصة بمشروع AllAffiliate_Agent.

يجب الالتزام بجميع القواعد الواردة فيه أثناء تطوير المشروع.

أي تعديل على أسلوب التطوير يجب أن يُوثق هنا أولاً.

---

# 2. General Principles

جميع أجزاء المشروع يجب أن تعتمد على المبادئ التالية:

- الوضوح.
- البساطة.
- القابلية للصيانة.
- القابلية للتوسع.
- الفصل بين المسؤوليات.
- الاستقرار.
- سهولة الاختبار.

---

# 3. Development Philosophy

يعتمد المشروع على فلسفة ثابتة:

- بناء النواة أولاً.
- اختبار كل مرحلة.
- عدم الانتقال إلى المرحلة التالية قبل استقرار الحالية.
- كتابة ملفات كاملة.
- تقليل الترابط بين المكونات.
- زيادة قابلية إعادة الاستخدام.

---

# 4. Project Architecture Rules

- يمنع تغيير المعمارية بدون قرار رسمي.
- يمنع تجاوز الطبقات.
- يمنع ربط الطبقات مباشرة بطريقة تكسر التصميم.
- يمنع إنشاء تبعيات دائرية.
- يجب احترام حدود كل طبقة.

---

# 5. Core Layer Rules

Core مسؤول عن التنسيق فقط.

Core لا ينفذ أي عملية حقيقية.

Core لا يتعامل مع الملفات مباشرة.

Core لا يكتب ولا يقرأ البيانات.

Core ينسق فقط بين المكونات.

---

# 6. Agents Layer Rules

كل Agent مسؤول عن نوع واحد فقط من المهام.

الـ Agent لا يحتوي منطق تنفيذ.

الـ Agent لا يتعامل مباشرة مع الملفات.

الـ Agent لا يستدعي الخدمات مباشرة إلا من خلال الآلية المعتمدة في المشروع.

أي Agent جديد يجب أن يرث من BaseAgent.

---

# 7. Services Layer Rules

جميع العمليات الحقيقية تنفذ داخل Services.

كل Service مسؤولة عن مهمة واحدة فقط.

لا يجوز إنشاء Service متعددة المسؤوليات.

أي Service يجب أن تكون مستقلة وقابلة للاختبار.

---

# 8. Command Dispatcher Rules

CommandDispatcher هو المسؤول عن:

- تحليل الأوامر.
- اختيار الخدمة المناسبة.
- استدعاء الخدمة.
- إعادة النتيجة.

لا يحتوي CommandDispatcher على منطق تنفيذ خاص بالخدمات.

---

# 9. Router Rules

Router مسؤول فقط عن اختيار Agent المناسب.

لا يجوز تنفيذ أي عملية داخل Router.

لا يجوز وضع منطق الأعمال داخل Router.

---

# 10. Memory Rules

لا يجوز لأي مكون التعامل مباشرة مع ملفات الذاكرة.

جميع عمليات الذاكرة تتم من خلال الطبقة المخصصة لها.

Memory يجب أن تكون قابلة للاستبدال مستقبلاً.

---

# 11. Plugin Rules

أي إضافة جديدة يجب أن:

- تكون مستقلة.
- لا تعدل النواة.
- لا تعدل الخدمات الأساسية.
- يمكن تفعيلها أو تعطيلها.
- توثق بالكامل.

---

# 12. AI Integration Rules

طبقة الذكاء الاصطناعي يجب أن تكون مستقلة.

لا يجوز ربط المشروع بمزود واحد فقط.

يجب تصميم واجهة تسمح بتبديل مزود الذكاء الاصطناعي دون تعديل بقية المشروع.

---

# 13. File Management Rules

كل ملف مسؤول عن وظيفة واحدة فقط.

لا يجوز وضع أكثر من مسؤولية رئيسية داخل الملف.

أسماء الملفات يجب أن تكون واضحة.

يمنع تكرار الوظائف بين الملفات.

---

# 14. Coding Standards

الالتزام بمعايير Python الحديثة.

استخدام أسماء واضحة.

استخدام Type Hints عندما يكون ذلك مناسبًا.

تقليل التكرار.

كتابة كود بسيط وسهل القراءة.

كتابة تعليقات عند الحاجة فقط.

عدم كتابة كود غير مستخدم.

---

# 15. Error Handling

كل خطأ يجب أن:

- يُلتقط بطريقة مناسبة.
- يُعاد برسالة واضحة.
- لا يؤدي إلى توقف النظام بالكامل.
- يُسجل في نظام السجلات إذا كان خطأً مهمًا.

---

# 16. Logging Rules

يجب تسجيل:

- بدء التنفيذ.
- انتهاء التنفيذ.
- الأخطاء.
- التحذيرات.
- العمليات المهمة.

لا يجوز تسجيل المعلومات الحساسة.

---

# 17. Documentation Rules

أي تعديل مهم يجب أن يُوثق.

أي ملف جديد يجب أن يُضاف إلى PROJECT_STRUCTURE.md.

أي تغيير معماري يجب أن يُحدث في PROJECT_BLUEPRINT.md.

أي تقدم في المشروع يجب أن يُسجل في PROJECT_STATE.md.

أي إصدار جديد يجب أن يُسجل في CHANGELOG.md.

---

# 18. Testing Rules

قبل اعتماد أي ملف يجب:

- التأكد من صحة الاستيرادات.
- التأكد من عدم وجود أخطاء نحوية.
- اختبار الوظيفة الأساسية.
- اختبار حالات الفشل.
- التأكد من عدم كسر الملفات الأخرى.

---

# 19. Version Control Rules

الإصدارات تتبع الصيغة التالية:

v0.4

v0.4.1

v0.4.2

v0.5

v0.6

...

v1.0

كل إصدار يجب أن يحتوي على سجل تغييرات واضح.

---

# 20. Session Workflow

كل جلسة تطوير يجب أن تتبع الخطوات التالية:

1. تحديد الملف الحالي.

2. مراجعة الاعتماديات.

3. طلب الملفات اللازمة فقط عند الحاجة.

4. كتابة الملف بالكامل.

5. استبدال الملف.

6. اختبار الملف.

7. تحديث PROJECT_STATE.md.

8. الانتقال إلى الملف التالي.

لا يتم العمل على أكثر من ملف في وقت واحد إلا عند وجود اعتماد مباشر.

---

# 21. ChatGPT Collaboration Rules

عند استخدام ChatGPT في تطوير المشروع يجب الالتزام بما يلي:

- عدم افتراض محتوى أي ملف غير متوفر.
- طلب اسم الملف المطلوب فقط عند الحاجة.
- عدم إعادة هيكلة المشروع دون طلب صريح.
- عدم إنشاء ملفات خارج الخطة.
- كتابة ملفات كاملة بدلاً من أجزاء صغيرة.
- الحفاظ على التوافق مع الملفات المعتمدة.
- الالتزام بالمعمارية الرسمية.
- عدم حذف أو تعديل الملفات المعتمدة إلا بطلب مباشر.
- الاعتماد على PROJECT_BLUEPRINT.md وPROJECT_STATE.md وPROJECT_STRUCTURE.md وDEVELOPMENT_RULES.md كمرجع رسمي قبل اقتراح أي تعديل.

---

# 22. Forbidden Practices

يمنع ما يلي:

- وضع منطق التنفيذ داخل Agents.
- تنفيذ عمليات داخل Router.
- كسر المعمارية.
- إنشاء تبعيات دائرية.
- تكرار الكود.
- إنشاء ملفات غير موثقة.
- تعديل ملفات مستقرة دون سبب.
- تجاوز ServiceContainer إذا كان هو آلية حقن الخدمات المعتمدة.
- كتابة كود غير مستخدم.
- إضافة ميزات جديدة قبل استقرار المرحلة الحالية.

---

# 23. Code Review Checklist

قبل اعتماد أي ملف يجب التأكد من:

☐ يحقق مسؤولية واحدة فقط.

☐ متوافق مع المعمارية.

☐ لا يحتوي تكرارًا غير ضروري.

☐ لا يكسر الملفات الأخرى.

☐ تمت مراجعة الأخطاء المحتملة.

☐ تمت كتابة الكود بأسلوب واضح.

☐ تمت مراعاة سهولة الصيانة.

☐ تم اختبار الوظيفة الأساسية.

☐ تم تحديث الوثائق إذا لزم الأمر.

---

# 24. Definition of Done

يُعتبر الملف منتهيًا فقط إذا تحققت جميع الشروط التالية:

- الكود يعمل دون أخطاء معروفة.
- اجتاز الاختبارات المطلوبة.
- متوافق مع المعمارية.
- موثق عند الحاجة.
- لا يحتوي على منطق خارج مسؤوليته.
- لا يسبب كسرًا للمكونات الأخرى.
- يمكن دمجه في المشروع دون تعديلات إضافية.
- تم تحديث PROJECT_STATE.md إذا أثّر على حالة المشروع.
- تم تحديث CHANGELOG.md إذا كان التعديل جزءًا من إصدار جديد.
